## Testing intent

This test plan validates that the branch has a working, reviewable
app-wide UI customization foundation:

1. Global skin packages validate safely and do not enable raw CSS injection.
2. `SkinRoot` emits safe CSS variables and can wrap a migrated surface.
3. `SpacesOverview` proves the first visible skin/view-pack vertical slice.
4. Framework-first skin-aware primitives reduce manual `data-vd-*` attribute
   sprawl while preserving the semantic skin contract.
5. CI/local checks enforce skinability outcomes and view/controller boundaries.
6. `SkinEditorDialog` proves a second migrated customization surface with
   validation, preview, save/revert/import/export, and diagnostics.

This plan does **not** require production app wiring for the Skin Editor.
`vkvw-9yay.5 — Milestone 5: Migrate Skin Editor as second UI customization
surface` is currently accepted as a reusable proof surface. Production wiring is
tracked separately in `vkvw-9yay.12 — Wire Skin Editor into production app
settings and global appearance persistence`.

## User stories

### Story 1 — App operator scans a skinned dashboard

As a Vibe Dashboard user, I can open the dashboard/home surface and see the
SpacesOverview rendered with the active global skin. Alternate built-in skins
should materially change foreground/background/tone without breaking contrast,
full-height panel behavior, or scan speed.

### Story 2 — Developer validates skin customization boundaries

As a developer, I can run one local command that checks migrated UI
customization boundaries. The command should reject hardcoded foreground colors
and controller/view boundary regressions in migrated surfaces without forcing
every text node to carry `data-vd-text`.

### Story 3 — Skin author edits a package safely

As a skin author or internal developer, I can use the Skin Editor proof surface
to preview, validate, import, export, save, apply, and revert global skin state.
Failures should be shown as diagnostics and should not lose draft/import text.

### Story 4 — Framework author avoids markup sprawl

As a framework author, I can use shared skin-aware primitives for common text,
heading, action, badge, card, row, and icon semantics instead of manually
sprinkling repetitive `data-vd-*` attributes throughout view files.

## Error testing notes

The following failures are important and should be recorded explicitly if seen:

- OpenLint/`ol` missing from PATH in CI or local test environment.
- `ast-grep` missing when running the repo-owned OpenLint policy.
- Storybook story fails to load for SpacesOverview or Skin Editor.
- Alternate skin renders unreadable text on light/dark backgrounds.
- Skin Editor save/import rejection produces no diagnostic.
- Skin Editor draft/import text is lost after failed save.
- Native color swatch modifies a schema-valid text token.
- Any view/controller boundary check fails due controller-owned intrinsic JSX.

## Independent tester result schema

Record results on the tester bead as JSON keyed by test case ID:

```json
{
  "TEST_CASE_1A": {
    "status": "PASS",
    "notes": "Commands and summary here"
  },
  "TEST_CASE_3B": {
    "status": "FAIL",
    "notes": "Expected readable alternate skin text; observed low contrast in heading. Screenshot: /tmp/example.png"
  }
}
```

Allowed statuses:

- `PASS`
- `FAIL`
- `BLOCKED`
- `SKIPPED`

For failures, include:

- exact command or UI step;
- expected result;
- actual result;
- URL/run ID/screenshot/snapshot path;
- smallest actionable fix needed.
